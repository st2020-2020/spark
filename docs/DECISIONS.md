# 决策记录

记录影响产品方向、架构或协作方式的关键决定，新条目写在最上方。已确定的产品基线见 [HANDOFF.md 决策状态](HANDOFF.md#决策状态)，本文补充迭代过程中做出的具体取舍。

每条包含：编号、日期、状态（采纳 / 待确认 / 已取代）、背景、决定、理由与影响。决定被推翻时不删除原条目，把状态改为「已取代」并指向新条目。

## D-0021 在私有暂存完成后发布移动端文件

- **日期与状态** 2026-11-22，采纳。
- **决定** 保存图片和导出 ZIP 先写入应用私有暂存。导出单次上限 256 MiB、保留 64 MiB 可用空间。Android 10+ 发布待定条目前后复核会话。Android 7–9 在 SAF 写入前后复核，失效时尝试删除外部文件。
- **理由** 私有暂存把下载中断、超限和发布分开处理，可以清理残件并在发布边界核对发起账号。SAF 的文档可见性与删除结果由外部提供者控制。[移动端桥接契约](design/MOBILE.md#43-受控双向消息通道)

## D-0020 按收藏提交的确定结果解冻草稿

- **日期与状态** 2026-11-22，采纳。
- **决定** 收藏提交明确拒绝时解冻本机草稿。校验失败及明确冲突 `duplicate_resource`、`idempotency_mismatch` 允许用户修改后生成新 UUID。`operation_in_progress`、结果不明的冲突、超时和断线保留原 UUID 与内容。重试先按原 UUID 核对收件箱。
- **理由** 服务端可能在客户端连接中断或同键请求处理期间完成写入。保留原键可延续同一次保存。明确拒绝时换键可以让用户修订输入。[服务端幂等与版本约定](design/API.md#幂等与版本)

## D-0019 移动工作区只加载同源 GET 主文档

- **日期与状态** 2026-11-22，采纳。
- **背景与理由** Android 的 `shouldOverrideUrlLoading` 不处理 POST，`shouldInterceptRequest` 只收到重定向链的首个地址。拦截首跳可以避免 307 或 308 转发主文档表单内容。
- **决定与影响** WebView 中的主文档请求限于同源 GET，用户主动点击的外链经路由规则交给系统浏览器。登录、其他表单与附件上传使用现有子资源请求。详见 [移动端导航规则](design/MOBILE.md) 和 [Android WebViewClient 文档](https://developer.android.com/reference/android/webkit/WebViewClient)。

## D-0018 移动端采用统一契约与双原生轻量工程

- **日期 / 状态**：2026-11-21 / 待确认（设计评审）
- **背景**：当前 `main` 上的 Android 客户端仍为 v0.1.0 极简 Java 原型（缺少文件选择、图片分享、下载与主题联动），而在线 Web 已迭代至 v0.7.0；后续明确需要同时支持 Android 与 iOS，需在体验、多端一致性与长期维护成本间定型架构。
- **决定**：
  1. 延续并升级「移动端共用在线 Web 工作区、原生负责系统融合与收集入口」的混合原生方向（吸收未合入分支 `feat/android-mobile-shell` 中的安全路由与分端升级原则）。
  2. **Android 与 iOS 采用独立原生工程线**（`apps/android/` 使用 Kotlin + Jetpack Compose + Material 3 + Room + OkHttp；未来 `apps/ios/` 使用 Swift + SwiftUI + `WKWebView`），不引入 React Native / Flutter 跨平台 UI 运行时，现阶段也不提前引入 KMP。
  3. **强统一四项资产**：共用 `apps/web/` 工作区、共用 `contracts/` 契约、建立平台中立的 Web ↔ 移动端桥接协议（`SparkMobile/1`，向后兼容 `SparkAndroid/2`）、对齐「灵光手帐」视觉令牌与草稿状态机。
  4. **鉴权分两阶段演进**：Android 重构首期继续复用同源 Cookie 实现零后端改动交付；iOS Share Extension（独立进程，120 MiB 内存红线）启动前引入可撤销设备级访问令牌（对齐 [v0.7 扩展凭据模型](releases/v0.7.md#第二批接口与交互设计)）。
- **理由**：在线工作区已承担大部分高频演进界面，跨平台 UI 框架不仅带来双倍维护，还在 iOS Share Extension 进程中面临 120 MiB 内存 OOM 风险；双原生轻量工程配合统一桥接协议，既能让两端系统分享、相册、下载与视觉达到成熟原生水准，又保持极低维护负担，并在未来 M7 离线同步阶段可平滑演进。
- **影响**：新增架构与工程设计主文档 [design/MOBILE.md](design/MOBILE.md)；`apps/web/` 后续新增移动端能力统一接入平台中立协议，不再新增 Android 专属硬编码入口。

## D-0017 v0.7 暂缓开发微信转发收藏

2026-11-21 采纳。当前已确认用户的腾讯云账号为个人主体；本轮没有可核验的公众号后台权限或经授权的收件测试账号。文章转发是否能稳定得到可保存的来源网址、图片是否可下载，以及实际费用，均缺少该账号的验证记录。现阶段继续提供网页收集和已有的 Android 分享入口，将开发资源用于可以通过真实浏览器独立验收的扩展。

如后续具备已授权的公众号，在其后台确认可用消息类型、媒体获取权限、配额和费用，用一篇合成文章及一张合成图片验证来源字段与重复投递。账号绑定方案须由已登录的 Spark 用户确认、能解绑，回调只保存明确转发的材料。未绑定时不归入账号，解绑后停止接收；原始回调、凭证和临时媒体地址不进入业务日志。该验证通过后再决定是否排入开发。

## D-0016 服务端直接使用平台 OSS 凭据

2026-11-19 采纳。共享桶由平台统一配置 AK/SK。服务端持有长期凭据，对浏览器仅签发单对象、限时、指定方法的访问 URL。采用此方式解决平台 RAM 用户与原角色实际删除权限不一致的问题。服务端承载长期密钥，相应进程的云端权限取决于平台 RAM 用户；限制挂载范围、隔离环境前缀并对日志中的授权 URL 保密。详见 [v0.3 附件设计](releases/v0.3.md#31-上传与附件f-02)。

## D-0015 图片分析一次外呼并共享日预算

2026-11-19 采纳。用户独立同意后，同一附件使用一次非思考多模态调用生成图中文字与画面描述。使用真实图片提取作业关联费用并复用文字整理占用的平台和用户日额度。派发前持久化预留，使发送结果无法确认时仍可对账。采用峰值未命中价格估算，实际厂商试用单列验收。[图片理解](releases/v0.3.md#32-图片理解f-02)

## D-0014 在独立持久存储保留删除回执

2026-11-19 采纳。清理进程将按操作 ID 命名的不可变回执写入独立持久存储，将文件和目录同步后再清理数据库与对象。回执保留对象版本和暂存上传到期时间。恢复进程只读回执，重建墓碑并在恢复环境重排对象清理。取舍和运行步骤见 [后端说明](../server/README.md#永久删除与备份重放v03-t08)。

## D-0013 网页提取使用独立出口和 Worker

2026-11-19 采纳。网页提取接触由用户保存的公网地址，使用独立进程、开关和 HTTP 客户端，使出口授权可以单独配置和撤销。结果隔离在收藏的当前内容版本中，站点失败时仍可使用原始收藏。运行方式见 [后端说明](../server/README.md#网页信息提取v03-t06)。

## D-0012 图片资产任务与文字 AI 分别启动

2026-11-19 采纳。同一发布镜像通过 `/spark-worker assets` 单独消费图片资产队列，以便 OSS 在文字 AI 和 OCR 关闭时仍可执行确认与清理。文字 AI Worker 沿用原启动条件、试用范围和用户同意检查。两个进程各自使用所需的只读凭证文件。运行方式见 [后端说明](../server/README.md#图片附件与独立资产-workerv03-t03)。

## D-0011 删除账本先记录意图

2026-11-19 采纳。永久删除请求在数据库事务内写入删除标记、变更事件和对象键，收藏立即从接口隐藏。独立清单复制、对象删除和数据库物理清理由清理任务完成。账本在收藏删除后按账号与收藏 ID 保留，供始终使用同一组对象键重试并阻止旧创建请求复活收藏。详见 [删除与恢复](design/DATA.md#删除与恢复)。

## D-0010 按完整版本部署到生产

2026-11-18 采纳。功能 PR 可以分别完成评审并合入主干。生产发布以完成整版任务、联调和审查的附注版本标签为准。只接受主干 SHA 的旧入口允许一个已合并的功能批次提前进入部署；现在生产脚本会在建立 SSH 连接前，校验远端版本标签指向指定主干提交。回退仍使用上次运行镜像与静态文件的备份。操作步骤见 [部署说明](../deploy/README.md)。

## D-0009 后续迭代按 v0.2 至 v0.7 拆分

- **日期 / 状态**：2026-11-18 / 采纳（各版本范围在进入开发前再确认）
- **背景**：候选需求较多，外部依赖（OSS、识别服务、邮件、服务器）到位时间不同。
- **决定**：v0.2 整理与信任（无外部依赖，可立即开始）→ v0.3 收集补齐 → v0.4 邀请内测发布 → v0.5 回访与时间 → v0.6 表达与效率 → v0.7 线索与渠道；正式发布前使用 `0.x` 版本号。
- **理由**：先交付不依赖外部服务的价值，同时为后续版本准备配置；内测发布前补齐收集与找回的核心闭环。
- **影响**：[版本规划](releases/README.md) 与各版本文档；ITERATION 第 6 节改为指向版本文档。

## D-0008 主干开发与 Conventional Commits

- **日期 / 状态**：2026-11-18 / 采纳
- **背景**：多人与多个 Agent 并行开发，需要统一的分支、提交与合并方式。
- **决定**：`main` 为唯一长期分支，只通过 PR 合入；短期分支按 `<类型>/<编号>-<描述>` 命名；提交采用 Conventional Commits；默认 Squash and merge，保持线性历史；以 `main` 上的附注标签发布。
- **理由**：规模小、发布节奏快，主干开发流程最简单；统一的提交格式便于生成变更记录。
- **影响**：规则见 [CONTRIBUTING.md](../CONTRIBUTING.md)。此前的提交不追溯修改。

## D-0006 产品定位与当前不做

- **日期 / 状态**：2026-11-18 / 待确认
- **背景**：迭代需要稳定的范围判断依据。
- **决定**：产品主线为「收集 → 归类到项目 → 找回」；当前不做团队协作与共享空间、公开社区与内容推荐、长文写作与文档排版、网页全文存档。

## D-0005 随手记与收件箱共用草稿

- **日期 / 状态**：2026-11-18 / 采纳
- **背景**：非收件箱页面需要不离开当前页就能记录。
- **决定**：随手记面板复用收件箱草稿作用域；在收件箱时原地聚焦内联收集框，两者不同时挂载。
- **理由**：避免平行草稿与数据丢失，沿用既有草稿、幂等与失败处理。
- **影响**：[WEB.md](design/WEB.md) 与 [WEB-VISUAL.md](design/WEB-VISUAL.md) 已同步。

## D-0004 Web 视觉采用「灵光手帐」与四套可切换配色

- **日期 / 状态**：2026-11-18 / 采纳
- **背景**：用户认为上一版观感不足、手机端尤其差，选定「小清新」方向并要求多套配色均可使用。
- **决定**：视觉概念为「灵光手帐」；提供薄荷晨雾（默认）、海盐蓝、抹茶奶白、樱花雾粉四套配色，各含深色版本；配色与明暗为两项独立的本机设置。
- **理由**：概念与「先收下、再整理」的产品主线一致；配色只替换令牌，组件不感知具体颜色，维护成本低。
- **影响**：规范见 [WEB-VISUAL.md](design/WEB-VISUAL.md)；配色暂不随账号同步（ITERATION O-06）。

- **背景**：本机没有完整运行环境，但视觉迭代需要看到界面。
