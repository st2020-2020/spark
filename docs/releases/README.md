本目录把产品规划拆成可交付的版本，并为每个版本维护一份设计开发文档。三份文档分工如下，内容不重复：

| 文档 | 回答的问题 |

| [ROADMAP.md](../ROADMAP.md) | 做到哪了：里程碑状态、进度与验证证据 |

## 1. 版本策略

### 1.1 版本号

- 采用 `MAJOR.MINOR.PATCH`。正式发布前处于 `0.x`：每个规划版本递增 MINOR（`0.2.0`、`0.3.0`…），修复递增 PATCH（`0.2.1`）。
- `1.0.0` 表示结束邀请内测、对外正式提供服务，届时另行约定兼容性承诺。
- 版本号统一体现在：Git 标签 `vX.Y.Z`、`apps/web/package.json` 的 `version`、[CHANGELOG.md](../CHANGELOG.md) 条目标题。

### 1.2 版本状态

| 状态 | 含义 |
| --- | --- |
| 规划中 | 范围已拆分，设计文档为草案 |
| 设计评审 | 技术设计完成，等待确认范围与接口 |
| 开发中 | 已确认，按任务拆分开发 |
| 验收中 | 功能完成，按测试计划在 OrbStack 联调验收 |
| 已发布 | 已打标签并记录 CHANGELOG；版本文档转为只读 |

### 1.3 准入与准出

**进入开发（准入）**

- 版本文档的范围、接口与数据变更、任务拆分已写完，待决事项有结论或有明确的默认处理。
- 依赖的外部配置（服务、密钥、资质）已到位，或在任务中标注为阻塞项。
- 涉及的契约变更已写入 `contracts/`（可先在功能分支中修改）。

**完成发布（准出）**

- 版本文档中的验收标准全部通过，并在 OrbStack 真实后端下验证；未能验证的项有书面说明。
- 各模块检查通过：Web 类型检查、测试与构建；后端测试、构建与 vet；桌面测试（若涉及）。
- 文档同步：PRODUCT / WEB / WEB-VISUAL / DATA / 契约按需更新，ROADMAP 记录验证证据，CHANGELOG 追加版本条目，ITERATION 标注已交付。
- 数据迁移可重复执行，并有备份与回滚说明。

依赖关系：


v0.2 不依赖任何外部服务，可以立即开始；v0.3 与 v0.4 的外部配置应在 v0.2 期间准备。

## v0.1 内测基线

当前代码已具备的能力，作为后续版本的起点，不单独建文档：

- 账号、邀请注册、会话与密码重置（开发邮件）；项目；文字与网址收藏、用途、编辑与冲突处理；手动归类与待归类；关键词搜索；已读；软删除与恢复；管理员导入邀请码。
- 平台 AI 文字整理（默认关闭，隔离环境已完成真实调用验证）。
- Web「灵光手帐」视觉、四套主题配色、随手记；Android 分享客户端源码。

收尾条件并入 v0.2 的 O-01：在 OrbStack 真实后端下完成首批业务与新视觉的浏览器复验。

## 3. 版本文档规范

- 新版本从 [TEMPLATE.md](TEMPLATE.md) 复制，文件名为 `vX.Y.md`。
- 任务编号格式为 `vX.Y-T##`；分支名引用需求或任务编号，见 [CONTRIBUTING.md](../../CONTRIBUTING.md)。
- 开发中范围变化要在版本文档的变更记录中写明，并同步本页总览。
- 版本发布后，文档状态改为「已发布」，不再修改；后续调整写入新版本文档。
