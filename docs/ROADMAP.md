M3 的文字整理子集可基于已落库的文字和用途先行，与 M2 附件并行。此次开发范围、角色分工及联调顺序见[平台 AI 整理设计](design/ORGANIZATION.md#首批实现约定)。网页抓取、图片 OCR、自动采纳项目和完整 M3 评测仍按各自依赖推进。

文字整理联调进度（2026-11-18）：后端报告在隔离 PostgreSQL、真实 River 和受控模型端点上验证了 v1 到 v2 迁移保留原文与版本、事务入队、零额度不发请求、并发竞争不超支，以及调低额度保留已预留和待对账金额。跨用户项目、虚假引文及未知来源被拒绝写入；处理中编辑、撤回授权、排除或删除收藏后，旧结果不会应用，已发生的调用仍计入账本。

部署在独立 OrbStack 项目中验证了 API、Worker、PostgreSQL 和本机 Magpie：零额度时无模型调用；分配额度后单次真实调用生成含正文和用途引文的项目建议，经 API 确认后持久化。该次调用使用 801 个输入及 169 个输出 token，按测试路由配置结算 1,480 微元，平台与用户账本的预留均归零。关闭 AI 并停止 Worker 后，新收藏恢复跳过整理。前端使用真实 API，在同条收藏上核对正文与用途引文，点击一次「加入项目」后决定版本从 v1 变为 v2；整页刷新后确认状态、理由和引文均保留。浏览器未发起重新整理请求。1440px 和 390px 视口均无横向溢出。增量修正后的前端类型检查、19 个测试及生产构建通过。第二独立厂商的真实回退未测，生产未启用。

后端在容器内使用 `spark_test` 随机 schema 通过 `CGO_ENABLED=0 go test ./... -count=1`、`CGO_ENABLED=0 go build ./...` 和 `go vet ./...`。故障注入验证了最后一次尝试中断后的恢复：遗留预留转为 `uncertain`，运行进入终态，恢复不再发出模型 HTTP 请求。

## 自动整理评测

先建立 40 条人工审阅样例，覆盖链接、截图、文字、混合输入，以及明确关联、多项目关联、无项目、识别失败和用户排除。初始材料使用公开可访问内容或明确标记的合成数据，随后补充用户自愿提供的真实收藏。

每条样例记录原始输入、已知可提取材料、项目描述、期望项目集合、禁止关联、关键主题、找回关键词和错误原因。开发样例与保留验证样例分开，参数调整后在保留集合复测。

自动关联精确率按正确自动关联数除以全部自动关联数计算，目标至少 90%；同时报告应关联资料中被正确自动关联的覆盖率。无自动关联时精确率记为无有效结果。样本数随内测增长，分输入类型报告结果。

对 OCR 记录关键文字能否找回，对摘要记录是否存在材料之外的事实，对项目理由记录是否能回指实际输入。误关联按内容提取、候选遗漏、模型判断和策略应用分别排查。

## 性能与恢复验证

建议首轮测试使用 20 个账号、每账号 1,000 条收藏，至少包含 100 条带中文提取长文的收藏。以总计 10 个并发客户端持续 15 分钟执行浏览、搜索和文本保存，另开 2 个后台整理任务。数据和负载均为测试配置，结果用于决定下一轮规模。

同地域测量文本保存确认 p95 目标小于 1 秒，关键词搜索 p95 目标小于 1 秒。记录失败率、CPU、内存、磁盘、数据库连接和队列等待时长。图片上传与外部模型时延单独测量。扩容依据为真实瓶颈、稳定性和增长趋势。

恢复演练在干净环境恢复数据库及附件关联，核对随机样本、已删除内容和登录状态。记录备份时间、数据损失窗口和实际恢复耗时，检验 RPO 15 分钟、RTO 2 小时的目标。
